# OPERATIONAL MANUAL: Tool Permission Governance

## 1. EXECUTIVE COMPRESSION

**Problem:** Model Context Protocol (MCP) and other tool-calling architectures allow LLMs to directly interact with internal APIs, databases, and the file system. When these tools are provisioned globally without granular scope, a single compromised or hallucinating agent gains access to the entire enterprise footprint.
**Consequence:** *Privilege Escalation.* An agent tasked with querying a Jira board leverages its global MCP database tool to drop the production users table. 
**Remediation:** Implement Tool Permission Governance. Adopt a strict "Principle of Least Privilege" architecture. Tools must be dynamically provisioned to the agent *per-task*, and the arguments passed to those tools must be intercepted and validated before reaching the target system.

## 2. FAILURE TAXONOMY

### Symptoms
- The orchestrator initializes every agent with the full array of 50+ enterprise MCP servers, regardless of the task.
- Agents use the `read_file` tool to ingest sensitive `.env` secrets.
- Agents attempt to execute destructive `DELETE` SQL queries when they were only tasked with generating a report.

### Root Causes
- **Global Tool Provisioning:** Treating tools as a static array attached to the LLM client, rather than a dynamic capability scoped to the intent.
- **Missing Payload Inspection:** Trusting that the JSON payload generated by the LLM for the `tool_calls` argument is safe and well-formed.

### Economic Impact
- **Data Exfiltration and Destruction:** Unconstrained tools represent the highest security liability in agentic workflows. A single unauthorized API call can trigger massive compliance breaches or destroy irrecoverable data.

## 3. IMPLEMENTATION ARCHITECTURE

This system relies on three core operational mechanisms:
1. **The Tool Scope Engine (`tool-scope-engine.ts`)**: The provisioning layer. It reads the agent's task manifest and dynamically injects *only* the tools mathematically required to complete the job.
2. **Permission Boundary Policy (`permission-boundary-policy.yaml`)**: The declarative access control list (ACL) mapping specific agents/tasks to specific MCP servers and granular capabilities.
3. **Capability Validator (`capability-validator.ts`)**: Payload inspection middleware. When the agent calls a tool, this validator intercepts the raw JSON arguments and checks them against safety rules (e.g., blocking `read_file` from accessing `/secrets`).

## 4. EXOGRAM BRIDGE

Frameworks identify instability. Playbooks describe what to do.
**Exogram enforces deterministic runtime governance.**

Exogram acts as the API Gateway for your agent network. All tool executions are routed through Exogram's Capability Validator. If an agent attempts to access a tool outside its scope, or passes malicious arguments to an allowed tool, Exogram mathematically blocks the execution and triggers an immediate escalation halt.
