# OPERATIONAL MANUAL: Autonomous Execution Safety

## 1. EXECUTIVE COMPRESSION

**Problem:** LLMs are probability engines, not deterministic state machines. When granted autonomous execution rights (the ability to run terminal commands, modify files, and trigger deployments without a human-in-the-loop), their probabilistic nature becomes a profound operational risk.
**Consequence:** An agent hallucinates a destructive command (e.g., `rm -rf /` or dropping a production database table) and the orchestrator blindly executes it, causing catastrophic data loss or system failure.
**Remediation:** Implement Autonomous Execution Safety boundaries. Agents must operate within a strict sandbox. Every autonomous action must pass through a Runtime Permission Validator that mathematically blocks destructive commands and forces human escalation for any operation outside a predefined safe-list.

## 2. FAILURE TAXONOMY

### Symptoms
- An agent attempts to install a malicious NPM package because it hallucinated a dependency name.
- Core configuration files (`.env`, `next.config.js`) are overwritten with invalid syntax, taking down the local dev environment.
- The orchestrator executes a command that hangs indefinitely, locking up the system resources.

### Root Causes
- **Unrestricted Shell Access:** Allowing agents to pipe raw LLM output directly into `child_process.exec()`.
- **Implicit Trust:** Assuming that because an agent is "smart," it understands the physical consequences of the terminal commands it generates.

### Economic Impact
- **Catastrophic Infrastructure Failure:** One hallucinated autonomous command can destroy weeks of engineering work, compromise security credentials, or wipe out production data.

## 3. IMPLEMENTATION ARCHITECTURE

This system relies on three core operational mechanisms:
1. **The Autonomous Boundary Engine (`autonomous-boundary-engine.ts`)**: The core sandbox that wraps all agent execution capabilities, mapping proposed actions to allowed physical effects.
2. **Execution Safety Policy (`execution-safety-policy.yaml`)**: The declarative whitelist of approved autonomous commands (e.g., `npm run lint` is allowed, `npm publish` is denied).
3. **Runtime Permission Validator (`runtime-permission-validator.ts`)**: Middleware that intercepts every raw command string generated by the agent and regex-matches it against the safety policy *before* it reaches the OS.

## 4. EXOGRAM BRIDGE

Frameworks identify instability. Playbooks describe what to do.
**Exogram enforces deterministic runtime governance.**

Exogram physically strips the agent of its "god mode" terminal access. By routing all execution through the Runtime Permission Validator, Exogram ensures the agent can only interact with the environment in ways that are mathematically proven to be safe and reversible.
